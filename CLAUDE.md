- **Government contracts scan was deadlocked by our own `Worker__MinSyncDate` — FIXED LOCALLY 2026-08-02** (upstream issue [#4272](https://github.com/daniel3303/Equibles/issues/4272)). `GovernmentContract` sat at **0 rows for 8 days** (scraper landed 2026-07-23 in #4213) with **108 consecutive failed cycles**. Root cause is an interaction, not a plain bug: on a cold start (no rows, no checkpoint) `GovernmentContractsImportService.ResolveStartDate` falls through to `SyncDateResolver.Resolve(default, …)` → the **global `Worker__MinSyncDate`**, which we set to `2000-01-01` (see the min-sync-date clamp note above). USAspending's `/api/v2/search/spending_by_award/` **hard-rejects any `start_date` before 2007-10-01 with HTTP 422** — verified directly: `2000-01-01`→422, `2007-01-01`→422, `2008-01-01`→200. ⚠️ **Why it never self-healed:** `Import` classifies *any* `HttpRequestException` as a transport failure ("systemic: every remaining window would fail identically") and rethrows to abort the whole cycle, but the checkpoint only advances via `AdvanceCheckpoint(windowEnd)` on a **successful** window — so the scan can never step past the bad date. That's right for a 5xx/DNS failure, wrong for a 422 (a permanent, window-specific rejection). There is **no govcontracts-specific start-date option**, so raising `Worker__MinSyncDate` is not an option — it's deliberately `2000-01-01` and would move every other scraper. **Local fix — seed the checkpoint at the API's floor:**
  ```sql
  INSERT INTO "GovernmentContractsScanState" ("Name","LastCompletedWindowEnd","UpdatedAt")
  VALUES ('award-scan', DATE '2007-09-30', now());
  ```
  Next cycle advanced `2007-09-30`→`2007-10-20` in ~20 s and persisted the first 77 awards. Backfill runs at **~1 one-day window/sec** (`WindowDays=1`), so 2007-10-01→today ≈ **6,880 windows ≈ 2 h**. ✅ **Backfill complete (verified 2026-08-09):** `GovernmentContract` at **47,152 rows**, `GovernmentContractsScanState.award-scan` caught up to the frontier (`LastCompletedWindowEnd = 2026-08-10`). **Relevance rose with the 2026-08-02 pull:** #4258 registered `AddGovernmentContracts()` on the self-hosted MCP server (62→64 tools), so this went from collecting nothing quietly to MCP tools returning nothing.

  ✅ **RESOLVED UPSTREAM 2026-08-09 — the seed is now redundant (but harmless, leave it).** Upstream shipped `769a4c1c` (PR #4273, `closes #4272`), which fixes this properly and goes further than either option offered in the issue:
  1. **Clamps every start-date resolution path to USAspending's 2007-10-01 epoch**, so a low global `Worker__MinSyncDate` is harmless instead of fatal — this is the change that retires the seed.
  2. **Reclassifies HTTP failures by what they actually say.** A 422 (the source's validation rejection) is treated as a *window-level* rejection: report it, scan the rest. Response-less/5xx/exhausted-429/408/global-401/403/404 still abort the cycle. ⚠️ Note the classifier defaults to **abort**, with 422 the *sole* exit — the reverse of what the issue proposed (blanket 4xx), because 400/405/410 usually indicate a source-wide defect that would otherwise fan out an Error row per window.
  3. **Caps window-failure fan-out at 5 consecutive failures** (422 is a whole-request rejection, so a bad request-invariant field rejects every window alike — thousands of Error rows while the worker still saw a "successful" cycle).
  4. **Retracts the checkpoint behind a failed window** instead of stepping over it, so a failed day can't age out of the trailing rescan lookback and lose its awards permanently. On a fresh install with no checkpoint row, the retraction *opens* the row behind the failure rather than returning early.

  ⚠️ **Known upstream trade-off:** a day that fails persistently now pins the checkpoint and the re-scanned range grows by one window per cycle — deliberately visible in the logs and the Errors page rather than silent. ⚠️ **Takes effect only once the new code is deployed** (`docker compose up -d --build`) — the clamp is in the worker binary, not config. A volume wipe *after* that deploy no longer needs the INSERT; before it, it still would.

  ⚠️ **Expected on the 2026-08-09 deploy — the checkpoint resets itself to 2007-09-30. This is by design; do NOT "fix" it.** Within seconds of the new worker booting, `GovernmentContractsScanState.award-scan` jumped from the caught-up frontier (`2026-08-10`) back to `2007-09-30`, with `MatchingVersion` 0→**2**. Cause: #4327 improved recipient resolution (SAM parent lookup + short distinctive names), and `ApplyMatchingVersionReset` pulls the cursor back to the epoch **once** whenever `RecipientMatchingVersion` (`GovernmentContractsImportService.cs:42`) exceeds the stored version. **Awards whose recipient can't be matched are dropped rather than stored, so a full re-walk is the only way a matching improvement reaches history** — re-fetched rows dedupe on `AwardUniqueKey`, so the count only grows (expect >47,152 once it completes; the ~2 h backfill estimate applies again). Unlike the checkpoint writes this reset is *not* best-effort — a persist failure fails the cycle deliberately, so the scan can't advance and re-stamp as current without having re-walked. ⚠️ **You will see no log line for this:** the "recipient matching upgraded (v0 -> v2)" message is `LogInformation`, and the worker container emits **WRN and above only** — same trap as the chunking pipeline. ## Git workflow

Two remotes: `origin` = `daniel3303/Equibles` (upstream, **read-only** — no push access), `fork` = `intobigdata/Equibles` (my backup). My ~5 local commits (equibles-cli, status scripts, port/compose config) ride on top of upstream `main`.

`pull.rebase true` is set (local + global), so updating is just:

```bash
git pull                              # rebases my local commits onto upstream's latest
git push --force-with-lease fork main # back up to my fork after a pull rewrote my commits
```

**Command phrase — "update equibles":** when John says *"update equibles"* (or "update the fork"), run the two steps above as one action: `git pull` first, then **only on a clean rebase** `git push --force-with-lease fork main`. **If the pull hits a merge/rebase conflict, STOP** — resolve or report it, do **not** force-push a half-rebased state to the fork. Report what came in from upstream after the pull.

- Use `--force-with-lease`, not plain `push`: a pull replays my commits with new hashes, so the fork needs the rewritten history. `--force-with-lease` is the safe force — it refuses if the fork has work I haven't seen.
- Upstream squash-merges everything, so `git branch --merged` lies about what's landed; check `gh pr list --repo daniel3303/Equibles` or grep `main`'s log instead.
