- **Web tabs clamp history to `Worker__MinSyncDate` (default `2020-01-01`).** Upstream PRs #3638/#3639/#3640 (merged 2026-06-10) made the price, short-data, holdings, insider, and congressional tabs hide anything *displayed* before the configured minimum sync date. ⚠️ **This is display-only — the data is still in the DB.** So if a stock's web history looks like it starts in 2020 but you know we ingested deeper (SEC docs back to ~2000, the pre-2002 dot-com archive, etc.), that's the clamp, not missing data. To surface the full depth in the UI, set `Worker__MinSyncDate=2000-01-01` in `.env` and recreate web (`docker compose up -d web`). MCP/DB reads are **not** clamped — only the web tabs.
- **XBRL dimensional-facts backfill is forced ON locally** via `XbrlCapture__BackfillEnabled=true` in `.env` (2026-06-11). Upstream #3622 defaults it OFF (their historical sweep drained); this machine never ran the sweep, so it's on to populate `FinancialFactDimension` for the back-catalogue (powers MCP `GetRevenueBreakdown`). Once it drains here (every doc `Captured`/`NotPresent`, cycle selects 0), it's safe to flip back off and recreate the worker. **Drained 2026-06-16 at ~48.7M `FinancialFactDimension` rows** (DB now ~359 GB). ⚠️ **Correction (2026-06-19):** the `DocumentManager.ChunkDocumentBatch` Postgres read timeout (`TimeoutException: Timeout during reading attempt`) was previously logged here as *"load contention, non-fatal, self-retries, clears once the grind drains, not a regression"* — **that was wrong.** It is an upstream defect: the chunking query (`NOT EXISTS Chunk` anti-join over the 150 GB `Chunk` table + `.Include(Content)` blob pull + `OrderBy(CreationTime)`/`Take`) exceeds Npgsql's 30 s default `CommandTimeout` and surfaces as `[FTL] Critical error in Document processor` **every cycle (~45 s)**. `EXPLAIN ANALYZE` confirms a `Nested Loop Anti Join` that probes `Chunk` once per document (**~1.14 M probes, 88–122 s**) — O(all documents), so it did **not** clear when the backfill drained: it still timed out on 2026-06-19 with a **fully drained backlog (0 pending docs)**, because the query is pathologically slow even when it returns nothing (~150–200 s and **~226 % DB CPU** per cycle). The `TimeoutException` is **caught by `BaseScraperWorker` (non-fatal to the host — it does *not* crash/restart the worker)**; the damage is the FTL spam, the wasted DB CPU, and chunking making zero progress while the query can't beat the timeout. ⚠️ **Separate issue — DIAGNOSED & FIXED (2026-06-19):** the worker *also* restarted on a ~12 min cadence (the original **293 restarts**), independent of the chunk query (it continued with the doc processor, stealth, AND Congress scrapers each disabled in turn — all three ruled out by A/B). Root cause: the **Docker VM was allocated only 7.75 GB on this 128 GB host**, so .NET's GC heap hard limit sat ~5.8 GB; a holdings/price worker's **bounded ~7–9 GB per-cycle allocation** (fires ~5 min after boot; exact worker not pinned) tipped it over, OOM-stopping the host *gracefully* (exit 0, no cgroup kill, no error logged) → `unless-stopped` restart. **Fixed by raising the Docker VM to 16 GB** (see the Docker VM ops note below) — confirmed survives both the ~6.4 GB (AUM rebuild, +5 min) and ~9.9 GB (`FundScoringWorker`, +10 min) spikes with ~1.7 GB margin. The allocation itself still exists (`BacktestPriceLoader` materialises the full per-holder price matrix → peak set by the largest filer; an upstream perf issue) but no longer restarts the worker. **Local mitigation:** `.env` sets `DocumentProcessor__Enabled=false` (the backlog is drained, so the pipeline has no work) + `Worker__CommandTimeoutSeconds=300` (safety net), backed by local edits to `DocumentProcessorWorker.cs` (env gate) and `Worker.Host/Program.cs` (configurable timeout). **Upstream:** still unfixed at #3817; issue #118 closed WONTFIX the `EnableRetryOnFailure` fix (deemed an unacceptable transaction-contract change), so the correct fix is query optimization — PR in progress.
- **Stealth browser enabled locally** (2026-06-16) for the IR-discovery + FDA-calendar scrapers (upstream stealth work #3700-3705/#3716/#3719). Enabled by setting `InvestorRelationsDiscovery__StealthFetch__SidecarUrl=http://cloakbrowser:9222` in `.env` on the **main worker** + running the sidecar with `docker compose --profile stealth up -d cloakbrowser`. ⚠️ Deliberately **not** using the compose `worker-stealth` profile service — it's a *second* worker that would run alongside `worker` and double-process every timer-based scraper. Caveats: CloakBrowser image is `linux/amd64` so it runs under **emulation** on this arm64 Mac (works, slower); it's an opaque 3rd-party binary kept isolated (internal-only `:9222`, pinned by digest). Disable: remove the `.env` line, `docker compose up -d worker`, then `docker compose --profile stealth down`.
- **Docker VM memory raised to 16 GB** (2026-06-19). Set via `"MemoryMiB": 16384` in `~/Library/Group Containers/group.com.docker/settings-store.json` (backup: `settings-store.json.bak-20260619`), then `docker desktop restart`. Verify: `docker info --format '{{.MemTotal}}'` → ~15.6 GB (.NET GC hard limit ≈ 75% ≈ 11.7 GB; worker peak ~9.9 GB → ~1.7 GB margin). **Why:** this host has 128 GB but Docker Desktop defaulted the VM to **7.75 GB**, starving the whole stack (the 359 GB Postgres' page cache *and* the worker). At 7.75 GB the worker hit .NET's GC heap hard limit (~5.8 GB) on the `FundScoringWorker`/AUM bulk per-cycle allocation and OOM-restarted every ~12 min — the **293-restart loop** (a *separate* issue from the chunk timeout above). ⚠️ **The 7.75 GB was Docker Desktop's DEFAULT, not set by Equibles** (no install script, no `mem_limit`/`deploy.resources` in compose, no `MemoryMiB` in settings-store before this) — so it's a host-level setting NOT captured by the repo; a Docker reset/reinstall reverts it and the loop returns. Re-apply via Settings → Resources → Memory or the `settings-store.json` key + Docker restart. (Upstream gap: the repo ships memory-hungry workers but documents no Docker memory requirement → anyone on the ~8 GB default hits the silent OOM loop. Drafting an upstream issue.)

## Git workflow

Two remotes: `origin` = `daniel3303/Equibles` (upstream, **read-only** — no push access), `fork` = `intobigdata/Equibles` (my backup). My ~5 local commits (equibles-cli, status scripts, port/compose config) ride on top of upstream `main`.

`pull.rebase true` is set (local + global), so updating is just:

```bash
git pull                              # rebases my local commits onto upstream's latest
git push --force-with-lease fork main # back up to my fork after a pull rewrote my commits
```

**Command phrase — "update equibles":** when John says *"update equibles"* (or "update the fork"), run the two steps above as one action: `git pull` first, then **only on a clean rebase** `git push --force-with-lease fork main`. **If the pull hits a merge/rebase conflict, STOP** — resolve or report it, do **not** force-push a half-rebased state to the fork. Report what came in from upstream after the pull.

- Use `--force-with-lease`, not plain `push`: a pull replays my commits with new hashes, so the fork needs the rewritten history. `--force-with-lease` is the safe force — it refuses if the fork has work I haven't seen.
- Upstream squash-merges everything, so `git branch --merged` lies about what's landed; check `gh pr list --repo daniel3303/Equibles` or grep `main`'s log instead.

### Contributing a fix upstream

Fork-PR flow (CLA already signed). **Branch off `origin/main`, not local `main`** — local `main` carries my personal commits that must not enter the PR: `git stash` → `git checkout -b fix/... origin/main` → `git stash pop` → commit → `git push -u fork <branch>` → `gh pr create --repo daniel3303/Equibles --base main --head intobigdata:<branch>`.

⚠️ **Run `dotnet csharpier format .` before pushing** (`dotnet tool restore` first if needed) — CI's `lint` job runs `csharpier check` tree-wide and fails the PR on any unformatted C#.
